# P3 — ERC-4337 accounts

**Goal:** Smart accounts use the **same tickets** as plaza/credits. Two arrows from Architecture.

## Arrow A — consume ticket (login / policy)

After P1 `issue()`, a 4337 **validator**, **paymaster**, or **session-key minter** checks:

- issuer signature (EIP-712) or
- `EvidenceRegistry.hasEvidence(account, schemaId)` if we anchored the hash

UserOp must **not** verify a zkTLS blob. Web2 stays off-chain.

This is how “offline credential as 进门条” lands on the account stack you already have.

## Arrow B — account as source

`OnchainProver` reads owner, module, UserOp, token/NFT, logs → kernel `issue()` with `trust.assumption = SELF` (chain is the source). Relayer reads; the contract does not run HTTPS.

## Subject binding

Web2 ticket subject = 4337 address via EIP-1271 challenge. Without this, credits could pay the wrong account.

## Exit

- One validator or paymaster path: UserOp allowed iff ticket valid
- One onchain schema (e.g. module enabled / NFT held) issues a kernel ticket
- Plaza/credits still use the same ticket type
